# 6.3 — `selectedRange` object literal rebuilt every render (`FilterDateSection.tsx:38-42`)

**Verdict: not actionable. No code change made.**

## The claim

> `selectedRange` object literal is rebuilt every render, giving DayPicker a new `selected` identity each time. Low impact; tidy alongside 2.3.

The observation that `{ from: draft.startDate, to: draft.endDate }` is a fresh object on every render is factually true. The implied consequence — that this causes avoidable re-renders or re-computation downstream — does not hold in this codebase.

## Why it doesn't matter here

- `Calendar` (`src/components/ui/calendar.tsx`) is a plain function component (`function Calendar({...}) { ... }`), not wrapped in `React.memo`.
- `DateRangeCalendarPanel` (`src/components/transactions/DateRangeCalendarPanel/DateRangeCalendarPanel.tsx`) is likewise a plain `FC`, not memoized.
- `FilterDateSection`'s parent (`FilterBottomsheetContent`) re-renders on every `draft` change — which is exactly the condition under which `selectedRange`'s underlying values (`draft.startDate` / `draft.endDate`) actually change.

Since nothing between `FilterDateSection` and the DOM is identity-sensitive (no `React.memo`, no `useMemo`/`useEffect` in this codebase keyed on the `selected` prop's reference), the `Calendar`/`DateRangeCalendarPanel` subtree re-renders on every relevant state change regardless of whether `selectedRange` is a stable reference or not. Wrapping the object literal in `useMemo` would not skip a single render — it would only add a dependency array to maintain for zero behavioral or performance benefit.

## Conclusion

This is a case where the stated defect is technically true but consequence-free given the current component tree. Fixing it would be optimization theater. Revisit only if `Calendar` or `DateRangeCalendarPanel` is ever wrapped in `React.memo` for an unrelated reason — at that point object identity would start to matter and this note should be re-evaluated.
