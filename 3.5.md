# 3.5 — Accessibility gaps in the mobile two-step flow

**Verdict: valid. Fixed in part; one sub-item deliberately deferred.**

The review listed three gaps. Status of each:

## Fixed

**2. The accessible dialog name never changed.** `DrawerTitle` was hardcoded to `"Date filter"` while the visible `<h2>` changed between steps. Fixed by deleting the standalone `<DrawerTitle className="sr-only">Date filter</DrawerTitle>` from `DateRangeDropdownView.tsx` and instead rendering the step-specific heading **as** the `DrawerTitle` itself, in both branches of `DateRangeMobileSheet.tsx` ("Select Date" on step 1; "Custom Date" / "Custom Date Range" on step 2). `vaul` always has a title (both branches render one unconditionally), and the accessible name now tracks the visible step.

**3. Redundant headings.** Resolved by the same change — there is now exactly one heading per step, which is simultaneously the visible `<h2>`-style text and the `DrawerTitle`. The separate `sr-only` title is gone.

**1a. Forward focus management (the cheap half).** On entering the calendar step (`calendarMode` becomes truthy), focus now moves to the back button via a `ref` + `useEffect` in `DateRangeMobileSheet.tsx`. This is a straightforward focus move within elements already inside `vaul`'s existing focus trap, so it doesn't fight the trap.

## Update: 1b implemented — the original cost estimate above was wrong

A second automated review pass (from another session working the same branch) challenged the deferral above and turned out to be right about the cost, so this was revisited and completed.

**1b. Backward focus restoration** is now implemented. Verified live in the browser: open the mobile drawer, click "Custom Date Range", click Back — focus lands back on the "Custom Date Range" button, confirmed via `document.activeElement`.

What made the original estimate wrong:

- **"Remember which preset was clicked" was already redundant.** `calendarMode` (`"single" | "range"`) already encodes the answer 1:1 with the two custom presets (`custom_date` / `custom_range`) — that mapping was already hardcoded in three places in the shipped code (`useDateRangeDropdown.ts`, `DateRangeMobileSheet.tsx`'s own step-2 heading, `DateRangePresetList.tsx`'s `isActive` check). The only missing piece was making that value survive `handleBack` resetting `calendarMode` to `null` — one `useRef` latching the last non-null mode (`prevModeRef`), added in `DateRangeMobileSheet.tsx`.
- **"Refs per preset button" wasn't needed either.** `DateRangePresetList` already fully unmounts and remounts every time the sheet swaps between the preset-list step and the calendar step (the two steps are structurally different JSX subtrees, not one tree with conditional props) — so plain HTML `autoFocus` on the matching button (`DateRangePresetList.tsx`'s new `autoFocusValue` prop) does the job with no imperative ref API.

Net cost: ~15 lines across `DateRangeDropdown.utils.ts` (a `CALENDAR_MODE_TO_PRESET` map), `DateRangePresetList.tsx` (`autoFocusValue` prop), and `DateRangeMobileSheet.tsx` (`prevModeRef` + passing it through) — not the "new state plumbing across two components" originally claimed.

**On the accompanying claim that the 1a forward-focus effect had a mount-time race with `vaul`'s own initial focus handling:** examined but not adopted as stated. The suggested guard (`if (calendarMode && !prevModeRef.current)`) is behaviorally identical to the original effect for every reachable state transition in this app — `calendarMode` only ever becomes truthy from `null` (there's no direct `"single"` ↔ `"range"` transition in the state machine), so `prevModeRef.current` is always `null` at that point in both versions. The guard was still worth adding, but only because `prevModeRef` was needed for 1b, not because it changes the mount-focus behavior. Whether opening the drawer directly into step 2 (reopening an existing custom-date/range filter) actually races with `vaul`/Radix's own focus management is unverified — React runs child effects before parent effects, so if anything it's `vaul`'s own auto-focus that would win, not this component's. Left unaddressed; revisit with an actual repro if it's ever observed.
